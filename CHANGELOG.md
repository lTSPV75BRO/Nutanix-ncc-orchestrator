# Changelog

All notable changes to the Nutanix NCC Orchestrator are documented here.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

**Release checklist (for maintainers):** Ensure [`VERSION`](VERSION) matches the intended tag; default `main.Version` in code is `2.1.0` when not set via ldflags. Run `go vet ./...`, `go test -race ./...`, and `go build ./...` (and `go build ./cmd/ncc-mcp-server`). Confirm `k8s/` and `helm/` image tags match `VERSION`. Tag `v2.1.0` and create a GitHub release using the matching `RELEASE_NOTES_v*.md`; attach `ncc-orchestrator-*` standalone binaries, `ncc-v2-stack-*` archives, and `checksums.txt` only — **do not** attach standalone `ncc-api-server-*` / `ncc-ui-server-*` binaries (the v1.x self-updater would silently mis-select them; see [2.0.0] known-issue note below and the v2.0.1 selector fix).

## [2.1.0] - 2026-06-16

Major **authentication + autonomic-operations** release on top of a maintenance/hardening base. It adds full interactive **login and RBAC** (`admin` / `operator` / `viewer`) for the api-server — local password accounts, SAML SSO, and LDAP / Active Directory login, a first-run **admin bootstrap** (random password + forced change), runtime user & SSO management in the UI, role-bearing session cookies with CSRF, self-service **personal access tokens**, **cluster groups** for membership-based access control, **HTTPS by default** with in-app certificate management, and a Kubernetes **Secret-backed user store encrypted at rest**. On top of that it makes the v2 stack **self-running and self-healing**: a single native **supervisor** (`v2-supervise`) with a cross-platform **boot-service installer** (`v2-install-service`), a **systemd-timer scheduler backend** alongside cron, an active **`doctor --fix` self-heal subsystem** (config / storage / secrets / backups / runs / TLS / process / log remediations) surfaced in a new **System Health** panel, **operational `/metrics`** with a starter Grafana dashboard, optional **AES-256-GCM envelope encryption** for the file-backed user store, consistent **UTC-on-the-wire / browser-local-in-the-UI** timestamps, and a refreshed Schedule settings page. It also closes a checksum-verification gap in `v2-bootstrap`, adds notification observability and templating, hardens TLS / notifications / process supervision, exposes NCC run metrics over the api-server `/metrics` endpoint, adds OpenTelemetry tracing, adds `v2-backup`/`v2-restore`, improves the Windows self-update experience, refreshes dependencies, and carries out the first wave of the `goNCC.go` package extraction (six new `internal/` packages). No breaking changes; all v2.0.x invocations keep working. **Affiliation note:** independent open-source project; not affiliated with or endorsed by Nutanix, Inc.

### Added

- **systemd-timer scheduler backend (alongside cron) + first-class boot-service installer (`v2-install-service`).** Two related scheduling/boot improvements for systemd hosts:
  - **`create-schedule --type systemd`** installs the recurring NCC scan as a systemd **timer** (`ncc-sched-<task>.timer`) driving a oneshot **service** under `/etc/systemd/system`, instead of a crontab entry. It's a better fit than cron on a systemd host: the run executes with an explicit `WorkingDirectory` (anchored to the config file's directory — the cron `cwd`/relative-path footgun) and clean environment, output is captured per-run to the scheduler log via a small generated runner script (works on pre-240 systemd with no `append:`), **overlapping runs are prevented automatically** (systemd won't start a second activation of a `Type=oneshot` service while the previous run is active — the flock is unneeded), and `Persistent=true` **replays a run missed while the box was off**. The interval/`--cron` is translated to `OnCalendar`, **including day-of-week fields** — numbers (cron `0`/`7` = Sunday), 3-letter names, comma lists, ranges (incl. wrap-around like `5-0` = Fri..Sun), and steps are *enumerated* to systemd weekday names so cron's `Sun=0..Sat=6` and systemd's `Mon..Sun` ordering can't silently mistranslate; a restricted day-of-month **and** day-of-week together is rejected because cron ORs them while systemd ANDs them. Pinned by an expanded `TestCronToOnCalendar`. `--type auto --action list/remove` now also covers systemd timers so detection (Settings → Schedule "Installed" status) and cleanup are uniform across backends, and a **coexistence guard** removes any same-task entry on the *other* backend so a scan is never scheduled twice. Surfaced in the UI via a new "systemd timer (Linux)" option in Settings → Schedule (Advanced). Cron remains the default; nothing changes for existing installs. Pinned by `TestCronToOnCalendar`, `TestOnCalendarFromSchedule`, `TestSanitizeSystemdName`, `TestBuildSystemdScheduleUnits`, and `TestNormalizeScheduleTypeSystemd`.
  - **`v2-install-service` / `v2-uninstall-service`** register the stack **supervisor** (`v2-supervise`) with the platform service manager for reboot persistence, cross-platform: a `Type=simple` **systemd** service on Linux (with a best-effort SELinux `restorecon` so a binary under a home dir can be exec'd), a **Task Scheduler** task triggered *at system startup* (run as SYSTEM) on **Windows** — closing the gap where the Windows stack had no auto-start after reboot — and a **launchd** LaunchDaemon (`RunAtLoad`+`KeepAlive`) on **macOS**. `--print-only` previews the unit/task without applying it. Pinned by `TestSystemdSupervisorUnit`.
- **Schedule settings UI: effective-schedule summary, exact config path, next-run estimate, and systemd overlap clarity.** Settings → Schedule now surfaces a human-readable **effective schedule** (e.g. "Every 4 hours", or the cron expression), the **exact absolute config file** the scheduled run uses — so operators can verify *which* `config.yaml` the timer actually runs (the config-path footgun fixed below) — a friendly **backend** tag (systemd timer / cron / Windows Scheduled Task) with the detector, and an **approximate next run**. The "prevent overlapping runs (file lock)" toggle is shown disabled with a hint when the **systemd** backend is selected (systemd gates overlapping activations natively, so the lock is unneeded). `GET /api/v1/schedule/health` now also returns `config`, `every`, and `cron`.
- **Single supervisor binary for both reboot persistence and runtime supervision (`v2-supervise`).** The orchestrator gained a native, in-process foreground supervisor — `ncc-orchestrator v2-supervise` (also `v2-start --supervise`) — that unifies the two previously separate mechanisms for keeping the v2 stack up: the POSIX-sh self-heal loops (crash/hang recovery) and the systemd *oneshot* wrapper that replayed `v2-restart` on boot. A single long-lived process now launches and owns the `ncc-api-server` and `ncc-ui-server` children directly and keeps them alive with the **same policy** as the sh supervisor — liveness restarts, **HTTP `--health-check` probes** to catch a hung-but-alive process, **exponential backoff** (capped at 30s), and **cooldown-and-resume** once the per-window restart budget is exhausted — with graceful SIGTERM→SIGKILL child shutdown. Run it as a `Type=simple` systemd service (`Restart=always`): the OS keeps the supervisor alive across reboots and the supervisor keeps the stack alive across crashes/hangs, so the oneshot wrapper and the detached sh supervisors are no longer needed for a boot-persistent install. The supervisor writes `run/v2-supervisor.pid` (surfaced in `v2-status`, stopped first by `v2-stop` so it cascades a clean child shutdown, and tailed by `doctor`), reuses the `--self-heal-*` tuning flags, and on start **replays persisted `.ncc-v2-start.json` settings** for any flag not explicitly passed — so a reboot honors runtime changes such as TLS enabled from Settings → Access. Pinned by `TestSuperviseRestartsAndStops` and `TestSuperviseWaitTokenGatesStart`.
- **Consistent timezone handling: UTC on the wire, browser-local in the UI.** The backend already emitted nearly all timestamps as UTC RFC3339; the remaining report `GeneratedAt`/`Now` values were pinned to `.UTC()` so *every* timestamp the server produces is UTC. The frontend now routes all date/time rendering through a single `src/utils/datetime.ts` helper (`formatDateTime`/`formatDate`/`formatTime`/`relativeTime`/`localDateKey`) that parses backend values as instants — defensively treating any timezone-less string as UTC — and renders them in the **browser's local timezone**. This replaces the per-component `relativeTime`/`formatTime`/`new Date().toLocaleString()` copies (Dashboard, Insights, Settings, Runs, Schedule, Audit, Access, Tokens, System Health), fixes hover tooltips that previously showed raw UTC strings, and fixes build-date labels that used `toISOString().slice(0,10)` (which showed the UTC date, off-by-one near local midnight).
- **Settings → System Health panel + unified `/api/v1/health/diagnostics` endpoint.** The autonomic self-heal layer now has a first-class admin surface. A new **admin-only** `GET /api/v1/health/diagnostics` runs a read-only scan that merges the orchestrator's `doctor` self-heal checks (config, storage, secrets perms, backups, runs, TLS, processes, logs — via the `doctor --json` subprocess) with the api-server's live external-auth probes (LDAP/AD bind, SAML SP cert, clock skew) into one ranked list (fail → warn → ok), with an `overall` status and an ok/warn/fail summary; `POST` re-runs the orchestrator checks with `--fix` to apply the safe remediations and re-probes auth, returning the post-fix state (audited as `health.diagnostics.heal`). The new **Settings → System Health** tab visualizes this — per-category cards, status tags, auto-fixed/hint annotations, a one-click **Heal now** (with a confirm describing exactly what the fixers do), a **Re-scan** button, and an "auto-heal loop on" badge when `--self-heal-interval` is set. Reuses the cached periodic report when available and exposes the same `ncc_selfheal_*` metrics.
- **Encrypted backups (`v2-backup --encrypt`).** A backup archive is a secrets bundle (API token, bcrypt hashes, SAML SP key, LDAP bind password, and usually a `config.yaml` with a plaintext Prism password); the on-disk file is `0600`, but once it's downloaded or copied off the host those secrets are plaintext. `v2-backup --encrypt` now seals the finished `.tar.gz` with **AES-256-GCM** (verify-after-create runs on the plaintext first, then the file is sealed), and `v2-restore` **transparently detects and decrypts** it — an unencrypted archive restores exactly as before. Key material is independent of the user-store master key: a **passphrase** (`--passphrase` / `NCC_BACKUP_PASSPHRASE`, scrypt-derived with a per-archive random salt) or a **raw 32-byte key** (`--key-file` / `NCC_BACKUP_KEY_FILE`, or inline `NCC_BACKUP_KEY`; base64 or hex). The envelope (magic + mode + salt) is GCM additional-authenticated-data, so a wrong key/passphrase or any tampering fails closed instead of restoring garbage, and `--verify-only` decrypts then validates. Pinned by `TestEncryptedBackupRoundTrip`. The **web UI exposes this too**: *Settings → Access → Backup & restore* → **Download backup** now offers an optional passphrase (encrypts the download; saved as `…tar.gz.enc`), and **Restore from file…** accepts a passphrase for encrypted archives. The api-server carries the passphrase to the `v2-backup`/`v2-restore` child via `NCC_BACKUP_PASSPHRASE` in the environment (download passphrase travels in the `X-NCC-Backup-Passphrase` header, restore in a multipart field) so it never appears in a URL, the process listing, or the audit log. **Server-side snapshots** support it too: *Create snapshot* takes an optional passphrase (`POST /api/v1/settings/backups` with `{"passphrase":"…"}`, stored as `…tar.gz.enc`), the backups list and table flag which snapshots are **encrypted**, restoring an encrypted snapshot prompts for the passphrase (`POST /api/v1/settings/backups/restore`), and downloading one streams the opaque `.tar.gz.enc` envelope. The encrypt modals now require a **passphrase confirmation** and a minimum length, so a single typo can't produce an unrecoverable archive. **Automated rollback points are sealed too:** when a backup key is configured in the api-server environment (`NCC_BACKUP_KEY_FILE` / `NCC_BACKUP_KEY` / `NCC_BACKUP_PASSPHRASE`), the in-app updater's pre-update snapshot is written encrypted (`pre-update-<stamp>.tar.gz.enc`) and the auto-rollback restore decrypts it transparently with the same environment key; with no key configured behavior is unchanged. Server-side snapshots also honor an optional **retention cap** (`NCC_BACKUPS_RETAIN=N`) that prunes the oldest **manual** snapshots after each create while **never** touching pre-update rollback points. Pinned by `TestPruneManualBackupsKeepsRollbackPoints`.
- **`verify --online` checks the binary against GitHub checksums automatically.** `ncc-orchestrator verify` already printed the running executable's SHA-256 and a URL to compare it against by hand; it now takes an opt-in `--online` flag that fetches the matching release's `checksums.txt` from GitHub and reports **MATCH / MISMATCH / NOT FOUND** for the platform's `ncc-orchestrator-<os>-<arch>` asset, **exiting non-zero on a mismatch** so it's usable in CI / health checks. It verifies against the release whose tag equals the binary's stamped version (override with `--release <tag>`; repo override with `--repo`), skips locally-modified builds (`git_dirty=true`), and reuses the same hardened HTTP client and `checksums.txt` parser as `update`. The default `verify` stays offline and fast. Trust note: the checksum is fetched from the same repo that serves the binary, so it authenticates a corrupted/MITM'd download and pins the version — cryptographic provenance (signed checksums / GitHub artifact attestations) remains future work. Pinned by `TestFetchReleaseChecksum`.
- **Scheduled automatic (optionally encrypted) backups, with retention.** Server-side snapshots can now run on a fixed cadence from **Settings → Access → Scheduled backups** (`GET`/`PUT /api/v1/settings/backups/schedule`): pick a frequency (hourly … weekly), a retention count (keep newest N), and optionally **encrypt at rest** (AES-256-GCM). The schedule runs **in-process inside the api-server** rather than as a detached systemd timer/cron entry — deliberately, because only that process holds the backup-encryption key material (`NCC_BACKUP_*` in its environment), which a detached unit would not inherit, so it's the one place that can produce *encrypted* scheduled backups without writing secrets into a unit file (it's also cross-platform and reuses the exact `v2-backup` path as manual snapshots). Each run writes a timestamped `ncc-backup-<UTC>.tar.gz[.enc]` into `<install>/backups` (new `v2-backup --output-dir`), then prunes older **scheduled** archives to the retention count while never touching `manual-*` or `pre-update-*` rollback points; last-run status/time, the written file, and an approximate next-run are surfaced in the UI, and **Save and back up now** takes an immediate snapshot. Cadence is honored across restarts via persisted `last_run_at` (a backup missed while the stack was fully down simply runs at the next tick). Pinned by `TestParseEveryDuration`, `TestScheduledBackupDue`, `TestValidateBackupScheduleInput`, `TestScheduledBackupFileFromOutput`.
- **Notifications on operational failures (backup + self-heal), not just runs.** The notification layer now also alerts on **operational** failures, reusing the existing "run failure" toggle (an operator who asked to hear about failures wants these too — no new config knob or UI, and existing notification states keep working): a **failed backup snapshot** (manual, scheduled, or the updater's pre-update rollback point — the last aborts the update), and a **self-heal cycle that finds failing `doctor` checks**, sent only on a healthy→failing **transition** so a persistently-failing check doesn't alert every cycle. Delivered through the same Slack/webhook/email channels and recorded in delivery status.
- **Per-snapshot "Verify integrity" action (UI + API).** Each server-side snapshot in *Settings → Access → Backup & restore* gains a **Verify** button (and `POST /api/v1/settings/backups/verify`) that runs `v2-restore --verify-only` against it — checking gzip/tar integrity, the manifest, and confined paths **without touching the live stack** — so an admin can confirm a snapshot is actually restorable before trusting it as a recovery point. For an encrypted (`.tar.gz.enc`) snapshot the action prompts for the passphrase and a successful verify also confirms the passphrase decrypts it.
- **Signed releases — Ed25519 signature over `checksums.txt` (verify + updater).** Builds the cryptographic-provenance step that `verify --online` previously deferred. The maintainer generates an Ed25519 key (`ncc-orchestrator release-keygen`, hidden), keeps the private key offline, and the **public key is embedded in every binary** at build time (`-ldflags "-X main.releaseSigningPublicKeyB64=…"`, threaded through `binaryGO.txt` via `NCC_RELEASE_PUBKEY`). The release build signs `checksums.txt` (`release-sign`, gated on `NCC_RELEASE_SIGN_KEY`) and publishes the detached signature as `checksums.txt.sig`. On a signed build, **`verify --online` and the in-app updater verify that Ed25519 signature against the embedded key before trusting any hash** — so a tampered/MITM'd `checksums.txt` (which could otherwise let an attacker swap both the binary and its checksum) is rejected; an `INVALID` signature always fails, and `verify --online --require-signature` also fails on a missing signature. Verification is **stdlib-only** (no `gpg`/`cosign` dependency) and works offline against the embedded key. Unsigned/dev builds (no embedded key) degrade to `SKIPPED` and behave exactly as before. Pinned by `TestVerifyReleaseSignatureValidAndTampered`, `TestSignReleaseFileRoundTrip`, `TestVerifyReleaseSignatureSkippedWithoutKey`.
- **Notification delivery controls: quiet hours, maintenance windows, and throttling.** The api-server notification layer (run/backup/self-heal alerts) gained delivery gates so it can be trusted in production without alert fatigue: **quiet hours** (a recurring daily mute in a configurable IANA timezone, with an `allow_failures` exemption so pages still get through), **maintenance windows** (absolute time ranges that mute *all* alerts and also skip the in-process scheduled digest), and **throttling** (per-event `dedup_window_sec` to collapse repeats + a global `min_interval_sec` floor between any two sends). Manual test sends bypass the gates. Configured in the new **Settings → Notifications** admin tab (channels, events, quiet hours, maintenance windows, throttle, and digest — with per-channel **Test** buttons) or on `PUT /api/v1/settings/notifications` (`quiet` / `maintenance` / `throttle`). Pinned by `TestInQuietHours`, `TestInMaintenance`, `TestNotificationSuppressed`, `TestValidateNotificationControls`.
- **Scheduled NCC health digest email.** An opt-in recurring summary of the latest run's health (cluster ok/failed counts, FAIL/WARN/ERR totals, health score, and top policy violations) delivered over the configured channels on a fixed cadence (`digest: {enabled, every}` on `PUT /api/v1/settings/notifications`). It runs on the always-on api-server's in-process ticker, reads the canonical `run-summary.json` the dashboard already serves (no extra run triggered), honors active maintenance windows, and persists `last_sent_at` so cadence survives restarts. Pinned by `TestDigestDue`.
- **Audit log forwarding to syslog / SIEM.** The JSONL audit stream (logins, settings changes, run triggers, self-heal, backups) can now be shipped off-box for retention and alerting. Two flag-configured sinks, usable together: **HTTP** (`--audit-forward-http-url`, optional `--audit-forward-http-auth` header and `--audit-forward-http-splunk` HEC event-wrapping — works with Splunk HEC, Elastic, Loki, or a generic webhook) and **syslog** (`--audit-forward-syslog host:port` over `--audit-forward-syslog-network` udp/tcp, RFC5424 framing). Forwarding is best-effort and fully decoupled from request handling — lines go onto a bounded buffer drained by a background worker, so a slow/down collector never blocks an API request or the local audit write; dropped lines are counted in the new `ncc_audit_forward_dropped_total` metric.
- **API explorer shows every route, with the required role.** The Settings → API explorer previously rendered only the subset of endpoints present in `/api/v1/openapi.json` (it preferred the OpenAPI spec and never fell back), hiding routes that were only in `/api/v1/meta/routes` (e.g. all `/settings/backups*`, `/health/diagnostics`). It now **merges both sources by path** (OpenAPI detail where available, the full `meta/routes` catalog filling the rest), and each route shows a **required-role** tag (viewer/operator/admin) derived from the same `routeMinRole` logic the auth middleware enforces. The route catalog (`apiRouteCatalog`) is now the **single source of truth**: `buildOpenAPISpec` gap-fills the hand-authored spec from it (so every registered route is present with a summary, request example, and an `x-required-role` annotation) — `/docs/ui` (Swagger) and the explorer can no longer drift as routes are added. Pinned by `TestApiRouteCatalogInOpenAPI`.
- **Optional envelope encryption for the file-backed user store (secrets at rest).** The local user database (`.ncc-api-users.json`) holds the most sensitive material the orchestrator manages — bcrypt password hashes, personal-access-token SHA-256 hashes, the SAML SP private key, and the LDAP service-account **bind password**. On a plain-file install these sat in a `0600` JSON document (plaintext to anyone who can read the disk or a backup archive). Operators can now supply a **32-byte master key** and the api-server transparently wraps the whole document with **AES-256-GCM** on save and unwraps it on load (fresh random nonce per write; the envelope magic is GCM additional-authenticated-data). Key sources, first match wins: `NCC_MASTER_KEY` (base64 std/raw/url or hex), or `--users-db-key-file` / `NCC_MASTER_KEY_FILE` (a file holding the key — keep it **off** the protected disk/backup, e.g. a tmpfs, secret mount, or KMS-fetched file, so key and ciphertext are not co-located). With no key configured the store stays plaintext (unchanged, fully backward compatible), and enabling a key **never locks you out**: a legacy plaintext store is read as-is and upgraded to ciphertext on the next write. In Kubernetes the recommended path remains the Secret backend (encrypted at rest by etcd/KMS); this file envelope is for non-k8s installs that still want the on-disk store and backups unreadable without the master key. Pinned by `TestSealOpenRoundTrip`, `TestOpenWithWrongKeyFails`, `TestNoncesAreUnique`, `TestDecodeMasterKeyFormats`, `TestEncryptingBackendMigratesPlaintext`.
- **Operational `/metrics` (Prometheus) + starter Grafana dashboard.** The api-server `/metrics` endpoint now also exposes live operational series alongside the existing build/runtime/per-cluster metrics: concurrent-run gauges (`ncc_runs_running`, `ncc_runs_queued`, `ncc_runs_max_concurrent`), a run-duration summary (`ncc_run_duration_seconds_sum`/`_count` plus `ncc_run_last_duration_seconds`), authentication counters (`ncc_auth_logins_total`, `ncc_auth_login_failures_total`, `ncc_auth_lockouts_total`), and in-app-update outcomes (`ncc_update_applied_total`, `ncc_update_failed_total`). **Backup/update observability gauges** round this out: a server-side backup inventory (`ncc_backups{kind="manual|pre-update|other"}`, `ncc_backups_encrypted`, and `ncc_backup_last_timestamp_seconds` so a "no recent snapshot" alert is one PromQL query), and an update-availability pair (`ncc_update_available` + `ncc_update_check_timestamp_seconds`) populated from the last UI update check — emitted only after a check has run, so a stale `0` is never mistaken for "up to date", and never triggering the slow check at scrape time. A ready-to-import Grafana dashboard ships at `deploy/grafana/ncc-orchestrator-dashboard.json` (run throughput, run duration, login success/failure/lockouts, rate-limiter, update outcomes, process health), and `Prometheus.md` documents the new series and example queries.
- **Run-queue ETA in the Runs panel.** `GET /api/v1/runs/active` now reports each queued run's `queue_position` (1-based FIFO place) and an `avg_run_duration_sec` (mean of completed runs this process has seen). Settings → Runs → *Active & Queued Runs* surfaces these as "Queued · #N in line" plus a rough "~Xs ETA" estimate, on top of the existing per-run de-dup view (which clusters each run owns vs. skipped, and the owning run id).
- **TLS + process + log self-healing.** The UI server gained a built-in `--health-check` probe (loopback GET, exit 0/1) and the self-heal supervisor now uses it, so a *hung* (alive-but-unresponsive) UI process is detected and restarted, not just a crashed one (closing the API-only gap). New `doctor` checks: **TLS certificate validity** (parses the UI cert; warns <30 days / fails when expired; under `--fix` auto-renews the stack-managed *self-signed* cert in place with the same SANs — operator-supplied certs are never rewritten), **stale PID files** (detects pid files whose process is dead and removes them under `--fix` so a crashed stack can restart cleanly), and **log file sizes** (warns on logs over 50 MiB and rotates them to `<name>.1` under `--fix`). Pinned by `TestCheckStalePIDs`, `TestCheckLogSizes`, and `TestBuildUIHealthProbeCmd`.
- **Periodic config-drift self-heal (`--self-heal-interval`).** The api-server can run the orchestrator's `doctor` checks on a timer (e.g. `--self-heal-interval 1h`), caching the report for the diagnostics endpoint / System Health view and exposing `ncc_selfheal_runs_total`, `ncc_selfheal_fixes_total`, and the `ncc_selfheal_checks{status}` gauge. With `--self-heal-auto-fix` it applies safe remediations every cycle — continuously re-anchoring relative output paths (the scheduled-run footgun), recreating missing output dirs, tightening secret-file perms, and repairing the config — and audits each applied fix (`selfheal.autofix`). Disabled by default (interval 0). (Auto-rewriting an installed cron *entry* is intentionally left manual; the recurring cause — relative output paths — is corrected at the config level instead.)
- **Directory/SSO self-healing: live AD/LDAP + SAML health probes.** On-demand health probes for the external auth providers, surfaced through the diagnostics endpoint and System Health UI: an **LDAP/AD** credential-free connectivity probe (dial + service-account bind + base search, reusing the save-time `validate()`), **SAML SP certificate** validity (parses the SP cert and warns <30 days / fails when expired), and a **clock-skew** check that compares the host clock to the IdP host (via the metadata URL `Date` header) since SAML assertions are time-sensitive. By design these are non-mutating — an expiring SAML SP cert *warns* rather than auto-renews because rotating it changes the SP metadata the IdP trusts and must be re-shared (unlike the self-signed TLS cert, which is safe to auto-rotate; see TLS self-heal). Pinned by `TestCertExpiryStatus` / `TestHumanShortDur`.
- **Backup self-healing: verify-after-create, restore preflight, retention, disk guard, auto-backup.** Every backup is now read back and validated end-to-end immediately after it is written (gzip CRC + tar integrity + manifest present + ≥1 data file + no path traversal); an archive that fails is deleted rather than left as an unrestorable "backup". `v2-restore` runs the same validation as a preflight before touching the install dir, and a new `v2-restore --verify-only` reports an archive's integrity/metadata without restoring. `v2-backup --retain N` prunes to the newest N archives, a disk-space guard refuses to write a backup that wouldn't fit (avoiding truncated archives), and the output directory is auto-created. The `doctor` report gained a **newest-backup-restorable** check (validates the latest archive end-to-end) and the **backup-freshness** check now *takes and verifies a fresh backup* under `--fix` when none exists or the newest is stale (pruning to 7). Pinned by `TestVerifyBackupArchiveAndRetention`.
- **Run self-healing: failure classifier + bounded auto-retry + run-health diagnostics.** When a triggered run fails with a *recoverable* cause — rate-limit (HTTP 429), timeout, or network/TLS — the api-server now performs a single bounded auto-retry with a **safe mitigation** applied (rate-limit → `--max-parallel 2 --retry-max-attempts 8`; timeout/network → `--request-timeout 40s --max-parallel 2`), never overriding a flag the operator already set, and never retrying non-recoverable classes (auth, parser, unknown). The retry is audited (`run.auto_retry`) and counted via the new `ncc_run_auto_retries_total` metric; disable with `--disable-run-auto-retry`. The `doctor` self-heal report gained two run-monitoring checks — **most-recent-run health** (reads `run-summary.json`, surfaces failed/OK cluster counts and the dominant failure class with its recommended mitigation) and **run-output freshness** (warns when the latest run is >24h old, the signature of a broken schedule). Pinned by `TestClassifyRunOutput`, `TestMitigationArgsForClass`, and `TestDecideRunHeal`.
- **Active self-heal subsystem (`doctor --fix`) + lockout-proof secrets-at-rest.** A new check registry turns `ncc-orchestrator doctor` from a read-only diagnostic into an autonomic self-heal tool. - **Self-heal supervisor: health-probe restarts, exponential backoff, and cooldown-and-resume.** `v2-start --self-heal` previously only watched **liveness** (`kill -0` on the PID) — a process that was alive but **hung** (deadlock, stuck handler, wedged connection) was never restarted, and once the restart budget was spent the supervisor **exited permanently**, leaving the stack down until a manual `v2-restart`. The supervisor now (1) **health-probes a still-alive api-server** on an interval using its built-in `--health-check` mode (GET `/api/v1/health` over loopback — no `curl` dependency) and restarts it after `--self-heal-unhealthy-threshold` consecutive failures (default 3, probe every `--self-heal-probe-interval`, default 10s), catching hangs a liveness check misses; (2) applies **exponential backoff** (capped at 30s) between restarts so a tight crash-loop no longer burns the whole budget in a couple of seconds; and (3) **cools down for one window and resumes** instead of giving up forever when the budget is exhausted, so a prolonged-but-transient fault (disk full, downstream outage) still self-heals once it clears. The probe applies to the api-server (the UI supervisor stays liveness-only, as it has no self-probe), and only when the api-server is not terminating its own TLS. New settings persist in `.ncc-v2-start.json` and replay through `v2-restart`/post-restore restart. Authentication is **local-first, then AD fallback** — the built-in `admin` and break-glass local accounts keep working even when the directory is unreachable — using a **service-account bind + search + rebind** (default AD filter `(&(objectClass=user)(sAMAccountName=%s))`); an empty password is rejected before any bind so an anonymous bind can't masquerade as a login, and the username is escaped into the filter. AD groups map to local roles by group DN or CN (case-insensitive, highest match wins; e.g. `CN=NCC-Admins,OU=Groups,DC=corp,DC=example,DC=com=admin`) with a default-role fallback. Configure via startup flags (`--ldap-url` [comma-separated for failover], `--ldap-base-dn`, `--ldap-bind-dn`, `--ldap-bind-password`, `--ldap-user-filter`, `--ldap-username-attribute`, `--ldap-group-attribute`, `--ldap-role-map`, `--ldap-default-role`, `--ldap-start-tls`, `--ldap-ca-file`, `--ldap-insecure-skip-verify`) or at runtime in **Settings → Access → LDAP / Active Directory** (`GET/PUT /api/v1/settings/ldap`), hot-reloaded without a restart. A **Test connection** button (`POST /api/v1/settings/ldap/test`) authenticates a sample user to validate connectivity and role mapping before saving. The bind password is write-only: stored only in the `0600` user-store file or the Kubernetes Secret (encrypted at rest) and never returned by the API. Pinned by `TestParseLDAPRoleMap`, `TestLDAPRoleFromGroups`, `TestLDAPEmptyPasswordRejected`, `TestHandleLoginLocalFirstThenLDAP`.
- **Role-bearing session cookie + CSRF.** Browser sessions use an httpOnly, `SameSite=Strict` `ncc_session` cookie; mutating cookie requests must echo a double-submit CSRF token (`X-CSRF-Token` header / readable `ncc_csrf` cookie). Static-token automation is exempt. The cookie's `Secure` attribute is set **automatically when the UI is served over HTTPS** (the default) and dropped when running plain HTTP (`--ui-insecure-http`) so browsers still store it on a non-localhost host; `--cookie-secure`/`--cookie-insecure` force the behaviour explicitly (`v2-start` selects the right one). Pinned by `TestWithAuthCookieSessionRBACAndCSRF`, `TestStaticAdminTokenExemptFromCSRF`.
- **UI login screen, forced password-change gate, and role-aware controls.** The frontend bootstraps from `/api/v1/auth/me`, shows a login page (local form and/or "Sign in with SSO") when login is enabled, presents a blocking password-change screen for `must_change_password` accounts, hides the Settings nav/route from non-admins and the run-trigger button from viewers, and adds a user menu with role badge and sign-out. The Settings → Access tab manages local users and SAML/SSO. **External authentication (SAML and LDAP/AD) is presented under a single "External authentication" card with a provider dropdown** to switch which one you're editing; both providers remain independently configurable and can be enabled at the same time (the dropdown shows a live on/off badge for each), and switching does not disable or discard the other.
- **ui-server session forwarding.** `ncc-ui-server` auto-detects (via backend health) when interactive login is enabled and forwards each browser's session cookie/CSRF instead of injecting the shared admin token (avoiding privilege escalation). Override with `--login-mode {auto|on|off}`.
- **Audit entries are now attributed to the acting user + role.** `withAuth` stashes the resolved principal on the request context, so every audited action automatically records `user` (the account subject — a real username for local/SSO sessions, or the synthetic `static-admin-token` subject for token automation) and `role` alongside the client IP that was already captured. The admin account always reports role `admin`. The Settings → Audit table gains a **User** column, and the JSONL export carries the new fields.

### Security

- **Custom-CA and certificate-pinning options.** New `ca-bundle` (PEM of additional trusted CAs, verified against system roots + the bundle) and `pin-sha256` (comma-separated allowed server-cert SHA-256 fingerprints) provide safer alternatives to blanket `insecure-skip-verify`; pinning rejects a MITM cert that full-insecure mode would accept. Pinned by `TestNormalizePin` and `TestPinVerifier`.
- **Decoupled SMTP TLS verification.** New `smtp-insecure-skip-verify` controls SMTP STARTTLS verification independently of the Prism `insecure-skip-verify` flag, so a self-signed Prism cert no longer forces unverified mail delivery.
- **Optional webhook HMAC signing.** When `webhook-secret` is set, the webhook body is signed with HMAC-SHA256 and sent as `X-NCC-Signature: sha256=<hex>` so receivers can verify provenance. Pinned by `TestSignWebhookBody`.
- **Notification dead-lettering.** `notification-deadletter-dir` persists email/webhook/Slack payloads that fail to deliver after retries (with channel, cluster, and error) so a transient outage no longer silently loses the alert. Pinned by `TestWriteDeadLetter`.
- **Self-heal supervisor shell-injection hardening.** `startSelfHealSupervisor` now passes the service name through a shell-quoted `SERVICE_NAME` variable instead of concatenating it into the generated script's `echo` lines, closing a quoting/`$(...)` break-out vector.
- **Fixed a panic in the HTTP-dump password redactor.** `FuzzRedactJSONPasswordValue` found an out-of-range slice when a quoted value ended with a trailing backslash; the index is now clamped. This path runs whenever `log-http` is enabled.
- **Session invalidation on password change/reset.** Each local account carries a `token_gen` counter that is stamped into every session token it mints and bumped whenever the password is changed or reset. A changed/reset password therefore immediately invalidates all previously issued session cookies/bearer tokens (every other device is signed out); the acting user's change-password response re-issues a fresh cookie so their current session continues. Pinned by `TestSessionInvalidationOnPasswordChange` and `TestForcedPasswordChangeFlow`.
- **api-server Content-Security-Policy + response-header hardening.** Direct api-server responses now carry a `Content-Security-Policy` (`default-src 'none'` for API/JSON, a scoped policy for the two HTML help pages) plus `Cross-Origin-Opener-Policy: same-origin`, and the CORS `Access-Control-Allow-Headers` now includes `X-CSRF-Token` so the SPA's double-submit token works under cross-origin CORS. Pinned by `TestSecurityResponseHeaders`.
- **User-store master key no longer leaks into orchestrator child processes.** The api-server shells out to the orchestrator for runs, backups, restores, the detached restart, and the self-heal `doctor`. Those children inherited the full environment, including `NCC_MASTER_KEY` (the user-DB encryption key) — visible via `/proc/<pid>/environ` and re-inherited by anything the child itself spawned, even though the orchestrator only copies the *sealed* user DB as opaque bytes and never needs the key. Every orchestrator child is now launched with `NCC_MASTER_KEY` **scrubbed** from its environment (key-file sources are unaffected). Pinned by `TestScrubEnvDropsMasterKey`.
- **Backup restore hardened against decompression bombs + silent truncation.** `v2-restore` now streams each archive entry straight to disk in two passes (headers/validation, then bodies) instead of buffering the whole archive in memory, and enforces a **per-file cap (64 MiB), a total-size cap (512 MiB), and a max file count (10000)** shared with the verifier — so a malicious or corrupt archive (e.g. a tiny gzip that expands to gigabytes, reachable via the admin-only `POST /api/v1/settings/restore` upload) can no longer exhaust memory or disk. The verifier and restorer now use the **same per-file limit**, fixing a mismatch (verify allowed 64 MiB while restore truncated at 32 MiB) where a 32–64 MiB file could pass verification but be silently truncated on restore; an oversize file is now rejected rather than truncated. Pinned by `TestVerifyBackupArchiveEnforcesCaps`.

### Fixed

- **Scheduled runs created from the UI/API always run with an absolute config path.** The schedule handler passed the run's `config`/`log_path` through to `create-schedule` as-is, so a **relative** value (e.g. the stored `config.yaml`) was resolved by the orchestrator against the **api-server's own working directory** (`<install>/bin`) — producing a cron line / systemd unit whose runner couldn't find `config.yaml`. The scheduled scan then failed with `configuration validation failed: at least one cluster must be provided` (exit 2) and silently produced no output (the dashboard went stale while the timer kept firing). The api-server now **anchors the schedule's config and log paths to absolute, install-root paths** before persisting and applying them, and the **systemd backend refuses to install a config-less timer** (a systemd run executes from the unit's `WorkingDirectory`, not the operator's cwd) rather than installing one guaranteed to fail on its first activation. Settings → Schedule now shows the resolved absolute config so the path is verifiable.
- **A second `v2-supervise` no longer clobbers the running stack's pid files.** Launching `v2-supervise` (or `v2-start --supervise`) while a supervisor was already active failed to bind the ports (its children crash-looped on "address already in use") and, on exit, **deleted the shared `run/v2-*.pid` files of the live stack** — blinding `v2-status`/`v2-stop` even though the systemd-managed stack was still serving. The supervisor now **refuses to start when another live supervisor already owns `run/v2-supervisor.pid`**, leaving the running stack's state intact, and reports a clear "another supervisor is already running" error. Pinned by `TestSuperviseRefusesSecondInstance`.
- **Scheduled (cron) runs now write output where the API/UI reads it — regardless of working directory.** Relative `output-dir-logs` / `output-dir-filtered` (and a relative `run-history-dir`) in `config.yaml` are now **anchored to the config file's directory** instead of the process working directory. A cron job runs the orchestrator with an arbitrary cwd (often the invoking user's home, e.g. `/root`), so a relative `outputfiles` previously landed beside that cwd and silently diverged from the install-dir path the self-healed `ncc-api-server`/`ncc-ui-server` serve — the dashboard would show stale data even though the scan ran. Anchoring to the config dir makes a scheduled run write to the same place an interactive run from the install dir does, so the self-healed stack always picks up fresh results. Absolute paths and flag-only (no config file) runs are unchanged. Pinned by `TestResolveUnderBase`, `TestBindConfigAnchorsRelativeOutputDirsToConfigDir`.
- **SAML SSO now completes through the UI origin.** `ncc-ui-server` proxies `/saml/*` straight through to the api-server (previously only `/api/*` was proxied, so `/saml/login` and `/saml/acs` hit the SPA), and those paths bypass UI-specific header injection so the SP flow is handled by the backend. The SP's request-tracking cookie is issued `SameSite=None` so it survives the IdP's top-level **cross-site POST** to `/saml/acs` (valid because the UI runs over HTTPS), and `/saml/*` is exempt from the api-server CORS origin allowlist (the signed assertion + relay-state cookie are the security boundary), fixing the `origin not allowed` (`NCC_API_FORBIDDEN`) error seen when the IdP POSTed its assertion back.
- **Restore preserves host-specific networking and TLS settings.** `v2-restore` no longer overwrites the target host's `.ncc-v2-start.json` networking with the backup's values: CORS allowed origins, advertise/backend URLs, listen addresses, the `--ui-insecure-http` flag, and UI TLS cert/key paths are preserved from the restoring host, so restoring a backup taken elsewhere no longer produces an `origin not allowed` UI lockout or a dangling certificate path.
- **First admin login over plain HTTP no longer loops.** Session cookies are no longer forced `Secure` by default; the attribute now tracks whether the UI is on HTTPS, so a browser on a non-localhost HTTP host actually stores the session cookie and the forced password-change screen appears instead of bouncing back to the login form.
- **Login/SSO errors no longer masked by the UI-server token diagnostic.** `ncc-ui-server` previously rewrote *every* backend `401` into the "Backend rejected the UI server's API token…" message. It now only emits that diagnostic when the UI server itself supplied the rejected credential (token/minted-session modes) and never for `/api/v1/auth/*` or `/saml/*`, so a wrong password surfaces the backend's clear `invalid username or password` and SSO/session failures pass through unchanged.
- **Local accounts/roles/SSO config persist across `v2-stop`/`v2-start`.** `v2-start` now passes an explicit, install-dir-colocated `--users-db <install-dir>/.ncc-api-users.json` (new `--users-db` override flag) to the api-server, instead of relying on a working-directory-relative default that could differ between launches.
- **Clicking a cluster link no longer also opens the alert Details drawer.** In the dashboard Alerts table the cluster link (opens Prism in a new tab) was bubbling its click up to the row handler, which also opened the right-hand Details drawer. The link now stops propagation, matching the existing KB-link behavior; clicking elsewhere on the row still opens the drawer.

### Fixed

- **Windows: shipped `.exe` binaries are no longer reported as "not executable."** `v2-check`, `v2-start`, and the api-server's startup guard tested the Unix executable bit (`mode & 0o111`), which is always 0 on Windows — so `v2-check` failed with `orchestrator-bin / api-server / ui-server binary not executable` and `v2-start`'s api-server child exited 1 with `orchestrator binary is not executable: …\ncc-orchestrator.exe`, even after `Unblock-File`. The executability test now lives in `v2layout.IsExecutable` and is OS-aware: Windows checks the file extension against `PATHEXT` (default `.COM;.EXE;.BAT;.CMD`); Unix keeps the strict `mode & 0o111` check. Pinned by `TestIsExecutable`, `TestHasWindowsExecutableExt`, `TestHasWindowsExecutableExt_RespectsPATHEXT`.
- **`v2-check` / `v2-start` / `v2-stop` / `uninstall` now auto-detect the stack root from the running binary's location.** When invoked from `<X>/bin/<self>` and `<X>` looks like a v2 layout (contains `frontend-dist/` or `bin/ncc-api-server*`), the install-dir defaults to `<X>` instead of `<cwd>/.ncc-v2`. Secondary paths (`--config-path`, `--output-dir`, `--log-dir`, `--token-file`) default to `<install-dir>/<name>`. If `<install-dir>/config.yaml` is missing, falls back to `<install-dir>/example_config.yaml` with a warning. Resolves the user-reported `v2-check failed (5 issues)` when running from inside an extracted stack.
- **`v2-start` against the recommended layout no longer fails with `path escapes repo root`.** The api-server's `--repo-root` (path-traversal sandbox) was hardcoded to `os.Getwd()`. When the user ran `./ncc-orchestrator v2-start` from `<X>/bin/`, repo-root would be `<X>/bin` but the auto-resolved config-path / output-dir / token-file landed under `<X>` — outside the jail. `runV2Start` and `runV2Bootstrap`'s start-script generator now compute repo-root as the install-dir-or-CWD ancestor (the directory that contains both) and pre-resolve macOS `/tmp` → `/private/tmp` symlinks so the api-server's internal EvalSymlinks comparison sees a consistent prefix.
- **`v2-start` `--wait-ready` no longer hangs / times out when binding to a loopback IP.** `localHTTPURLFromListen` was rewriting `127.0.0.1:port` to `localhost:port` for both the wait-ready check and the UI→API backend URL. On macOS `localhost` resolves to `::1` (IPv6) first, but the api-server is bound IPv4-only, so the connection was refused even though the server was healthy. The helper now preserves the user-supplied host. The CORS allow-list separately gains the `http://localhost:port` form when the UI binds loopback so browsers reaching the UI under either name still succeed.
- **`orchestrator_bin` reported by `/api/v1/health` is now an absolute path that exists on disk.** Previously `resolveV2OrchestratorBin` returned `./ncc-orchestrator` (correct relative to the orchestrator's CWD), but the api-server interpreted it relative to its own CWD (= repo-root), producing a non-existent path. API-triggered runs would have failed to spawn the orchestrator. Helper now returns absolute, symlink-resolved paths.
- **Output extractor preserves executable mode bits** ([carry-over from in-flight 2.0.2 work]). `extractTarGzArchive` and `extractZipArchive` now use the mode in the archive header instead of hardcoded `0644`, so binaries inside `ncc-v2-stack-*.tar.gz` and `.zip` come out as `0755` after `update`.
- **Uninstall sweeps both legacy and new layouts.** `uninstall --remove-local` now adds install-dir-relative `outputfiles/`, `nccfiles/`, `promfiles/`, `logs/`, `.ncc-api-token`, `.ncc-api-schedule.json`, `.ncc-api-notifications.json` to the cleanup set in addition to the existing CWD-relative entries. Belt-and-braces for the rare `--remove-v2-runtime=false` path.

### Changed

- **`v2-check` / `v2-start` / `v2-stop` / `uninstall` flag defaults are now empty strings** instead of hardcoded `.ncc-v2` / `config.yaml` / `outputfiles` / `nccfiles` / `.ncc-api-token`. Empty values are resolved at runtime via the auto-detect logic above. Explicit values are honored as before.
- **README** quick-start updated to show the new no-flags flow first, with the explicit-flags form as the legacy / advanced fallback. Two new sections: "Run on macOS / Windows / Linux (trust & verification)" and "Running individual components (API only / UI only)".

- **`Dockerfile.api`** HEALTHCHECK now uses `ncc-api-server --health-check` instead of bundling `wget`. Drops the runtime-image dependency on a curl-equivalent.

## [2.0.1] - 2026-05-27

Patch release with one substantial behavior change: **`update` now upgrades the v2 stack as a single package, irrespective of which binary (orchestrator, api-server, ui-server, or any renamed variant) was invoked.** All v1.x users should upgrade via this release rather than v2.0.0.

### Changed

- **`update` is now a package-level operation** ([#9]). When the selected release publishes a `ncc-v2-stack-<os>-<arch>.{tar.gz,zip}` archive (true for v2.0.0+), `update` downloads it, verifies the SHA-256 against `checksums.txt`, extracts to a private temp dir, and atomically installs `bin/*` + `frontend-dist/` + `example_config.yaml` into the resolved install directory. The running binary is self-replaced from the canonical-or-basename-matched entry in the extracted `bin/`. Install-dir auto-detection: running from `<X>/bin/<self>` → install over `<X>`; otherwise install into the binary's directory. This makes the upgrade path identical regardless of which binary you ran or how you renamed it. For legacy v1.x releases without a stack archive, falls back to the original single-binary update path.
- **Legacy single-binary selector hardening (fallback path).** `pickAssetForCurrentPlatform` now prefers assets whose name starts with the running executable's basename (e.g. `ncc-orchestrator-*`) before falling back to the legacy first-match behavior. Retained as defense in depth even though the package-archive path is now primary.

### Fixed

- **`v2-bootstrap` / `v2-start` failed against the v2.0.0 stack archives** because the layout-check (`hasBootstrappedV2Layout`) only accepted canonical binary names (`bin/ncc-api-server`), but v2.0.0 stack archives packaged platform-suffixed names (`bin/ncc-api-server-<os>-<arch>`). The lookup helpers now accept either form, so existing v2.0.0 stack archives bootstrap cleanly, and future archives can converge on canonical names.
- **`pickAssetForCurrentPlatform` regression on multi-binary releases** ([#9]) — The original P0: GitHub returns release assets alphabetically, so when v2.0.0 shipped three binaries per platform the v1.x self-updater silently overwrote `ncc-orchestrator` with the api-server binary. Replaced by the package-update flow above; the legacy code path also got the basename-prefix selector fix as a fallback.
- **v2.0.0 release-asset layout hotfix (2026-05-27 19:35Z)** — As an immediate mitigation for users still on v1.x updaters, the 12 standalone `ncc-api-server-*` and `ncc-ui-server-*` assets were removed from the v2.0.0 release; the api-server and ui-server binaries continue to ship inside `ncc-v2-stack-*` archives.
- **macOS `._*` resource-fork sidecars** are no longer included in tarballs (`COPYFILE_DISABLE=1` + `--no-mac-metadata` honored by BSD tar).

### Build / packaging policy

- `binaryGO.txt` step 6 renames binaries inside the stack archive to canonical names (`bin/ncc-orchestrator`, `bin/ncc-api-server`, `bin/ncc-ui-server`) without platform suffix. Matches the v2-bootstrap expected layout.
- `binaryGO.txt` step 7 enforces the no-standalone-server-binaries publishing policy at build time (excluded from `checksums.txt` and therefore from publishable assets). Documented inline with rationale.
- `binaryGO.txt` step 0 exports `LDFLAGS` so the variable survives step-by-step shell invocation.
- Version metadata bumped to `2.0.1` across `VERSION`, `goNCC.go`, `cmd/ncc-api-server/main.go` (default `Version` + OpenAPI `info.version`), `cmd/ncc-mcp-server/main.go`, `helm/ncc-orchestrator/Chart.yaml`, `helm/ncc-orchestrator/values.yaml`, and the three k8s manifests.

### Tests

Seven tests / twenty sub-cases added covering the package selector, install-dir resolution, layout-check naming tolerance, the v2.0.0 regression path, and the legacy-release fallback.

### Migration

- **From v1.x:** Run `ncc-orchestrator update --allow-major-upgrade` against v2.0.1 (or v2.0.0 since the hotfix). The fixed selector picks `ncc-orchestrator-*` correctly.
- **From v2.0.0:** Run `ncc-orchestrator update`. No major upgrade flag needed.
- **From a corrupted v2.0.0 install** (api-server downloaded in place of orchestrator): Re-download `ncc-orchestrator-<os>-<arch>` directly from the v2.0.1 release page or run the recovery `curl` snippet documented in `RELEASE_NOTES_v2.0.0.md` → Known issues.

## [0.1.12] - 2026-02-12

### Added

- **Digest notifications**  
  New option `--notify-digest` (config: `notify-digest`) sends **one email, one webhook, and one Slack message per run** with a run overview (clusters OK/failed, duration) instead of per-cluster notifications. Optional attachment of the aggregated `index.html` to the digest email when `email-attach-html` is set; optional base64-encoded index in the webhook payload when `webhook-include-html` is set.

- **Run summary log**  
  At the end of each run, a single structured log line is emitted with `clusters_ok`, `clusters_failed`, `duration_s`, and `index_html` path for easier parsing and monitoring.

- **Notification retries**  
  Email and webhook sends are wrapped in a retry loop (3 attempts with jittered backoff using `retry-base-delay` / `retry-max-delay`) to improve reliability on transient failures.

- **Replay + HTML attach**  
  In replay mode, per-cluster HTML (and CSV) is generated **before** sending notifications. When `email-attach-html` is set, the generated HTML file is attached to the replay email; when `webhook-include-html` is set, the replay webhook payload includes the report as base64.

- **Config path validation**  
  `validateConfig` now requires non-empty (after trim) values for `output-dir-logs`, `output-dir-filtered`, `log-file`, and `prom-dir`, with clear error messages.

- **HTTP log redaction**  
  When `log-http` is enabled, request/response dumps redact the `Authorization` and `Cookie` headers, and mask JSON values for `"password"` / `"Password"` fields to avoid leaking secrets in logs.

- **Documentation**  
  - README: HTTP pool/timeouts description, example webhook payload, testing email and webhook (webhook.site, MailHog, Mailtrap), `--version` behavior, `notify-digest` and env vars.
  - k8s/README: Runbook for CronJob failures (logs, job-debug, NFS permissions, prune images).
  - k8s ConfigMap: `notify-digest: false` option added.

- **Unit tests**  
  New/updated tests for `validateConfig` (path validation), `checkOutputPermissions`, digest overview format, and `ParseSummary` (no-block and check-name cases).
